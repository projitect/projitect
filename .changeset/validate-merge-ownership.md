Validate JSON merge ownership before anything is written, and remove only the fields a blueprint wrote. Two blueprints claiming a key and one of its descendants (`scripts` and `scripts.test`) now fail with `pjt.plan.conflict-merge` in either declaration order, judged on dotted-path segments. A merge blueprint that writes a field its `ownedKeys` do not cover fails with the new `pjt.plan.unowned-merge-write`. One blueprint declaring a key and its own descendant owns the ancestor. `.pjt.lock` moves to version 3: each merge entry records the fields the blueprint wrote (`writtenPaths`), and removing a blueprint deletes only those fields, so children you added under an owned key and keys another blueprint claims stay. A version 1 or 2 lock stays readable and is rewritten as version 3 by the next `pjt remodel`; a lock written by version 3 is rejected by older projitect with `pjt.lock.version-mismatch`. When a blueprint leaves `.pjt.ts` while its pre-v3 lock entry only records a parent key over an object, `pjt remodel` refuses with the new `pjt.remove.ambiguous-merge-claim` before writing anything, and `pjt inspect` reports it. A merge write that would replace an array, string, number or `null` your file holds above an unowned field fails with the new `pjt.apply.merge-ancestor-not-object` before anything is written; removal leaves a recorded field that now holds an object with your children alone, and a blueprint that upgrades a field from a value to an object keeps the new fields. Major because the lockfile schema version bumps, which the versioning table rates as a breaking change.
