## Why projitect?

<CardGrid>
  <Card title="Composable blueprints" icon="puzzle">
    Drop blueprints into one file. Powered by **Effect**, so you get conditional logic, generator
    syntax, and typed errors for free — no shell scripts, no DSL.
  </Card>
  <Card title="Drift detection on every CI run" icon="approve-check">
    `pjt inspect` exits nonzero when your repo diverges from spec. No more *"works on my machine"*
    config rot. Add one line to your workflow and CI guarantees integrity.
  </Card>
  <Card title="Swap frameworks cleanly" icon="random">
    Remove a blueprint, the configuration it added is flagged. No orphaned `tsconfig` settings or
    stale `package.json` scripts when you migrate. Your repo stays as slim as your stack.
  </Card>
</CardGrid>

## What it looks like

Your project's blueprint file is one file at the root, called `.pjt.ts`:

```ts
import { pjt } from "@projitect/cli"
import { gitignores } from "@projitect/blueprint-gitignore"
import { vitest } from "@projitect/blueprint-vitest"
import { changesets } from "@projitect/blueprint-changesets"
import { markdownSnippets } from "@projitect/blueprint-markdown"
import { acmeSkills } from "@acme/agent-skills"
import { huskyLintStaged } from "@projitect/blueprint-husky-lint-staged"
import { tsconfig } from "@projitect/blueprint-tsconfig"

export default pjt({
  blueprints: [
    gitignores.macOs(),
    gitignores.node(),
    gitignores.vscode(),
    tsconfig(), // strict tsconfig.json, owned by the blueprint (no drift)
    vitest(), // vitest.config.ts + scripts + devDeps + coverage/ in .gitignore
    changesets(), // .changeset/config.json + release scripts + @changesets/cli
    markdownSnippets.agentsVerification(), // a versioned snippet in AGENTS.md
    huskyLintStaged(), // .husky/pre-commit + lint-staged config + husky devDeps
    acmeSkills, // a skill package built with skills(): installed under .claude/skills, drift-checked
  ],
})
```

That's the **whole spec**. For a React app, `react()` replaces `tsconfig()`, `vitest()` and
`gitignores.node()`: it composes them with Vite, React and TypeScript, owns the config, and seeds
starter source you keep. See the [react-setup example](/examples/react-setup/). For a Next.js App
Router app, `next()` does the same; see the [next-setup example](/examples/next-setup/).

Three commands act on it:

```bash
pjt init               # bootstrap projitect in this project
pjt remodel            # apply the blueprints to disk (non-destructive)
pjt inspect            # report drift (exit 1 in CI if the repo is out of spec)
pjt add <package>      # install a blueprint package and splice it into .pjt.ts
pjt build --force      # wipe and rebuild from scratch (requires clean git)
pjt explain <id>       # explain an error id
```

## See drift in action

After `pjt remodel`, your `.gitignore` has comment-fenced regions owned by each blueprint:

```text
# pjt:gitignore:macos start
.DS_Store
.AppleDouble
# ... rest of the macOS section ...
# pjt:gitignore:macos end
# pjt:gitignore:node start
node_modules/
.env
# ... rest of the Node section ...
# pjt:gitignore:node end
```

Now suppose a teammate hand-edits the file — say, they delete `.DS_Store`. Running
`pjt inspect` in CI catches it immediately:

```text
~ modify .gitignore — region pjt:gitignore:macos content drift
```

Exit code: `1`. PR fails. Run `pjt remodel` to fix.

## pjt runs in your browser

Edit a `.pjt.ts` and watch the plan and drift output update, with no install and no server. The
engine runs in your tab against an in-memory project.

## Status

**v0** ships all four ownership modes (region, merge, owned, seed), the `gitignore`, `tsconfig`,
`vitest`, `changesets`, `react` and `next` blueprints, plus `pjt init`, `pjt remodel`, `pjt inspect`, and
`pjt explain`. Effect v4 RC under the hood.

The `eslint` blueprint, exec and post-apply operations and the worker-process sandbox are on the
[roadmap](/docs/roadmap/).
