`@projitect/blueprint-eslint` exports two blueprints on the `eslint` namespace:

- `eslint.config()` owns a flat `eslint.config.mjs` (including its `ignores` list), merges the
  `lint` and `lint:fix` scripts into `package.json`, and adds `eslint`, `@eslint/js` and
  `typescript-eslint` to `devDependencies`. Your other scripts and dependencies are untouched.
- `eslint.fix()` is a post-apply command. `pjt build` and `pjt remodel` run `eslint --fix .` after
  every file operation has succeeded, applying available lint fixes to the resulting project.
  `pjt inspect` runs only `eslint .` and reports a failing check as drift (exit 1); it never
  changes a file.

In an initialized projitect project, add the configuration first. Keep `eslint.fix()` out of
the blueprint list until its executable is installed:

```bash
pnpm pjt add @projitect/blueprint-eslint
pnpm add -D typescript
pnpm pjt remodel
pnpm install
```

`add` inserts `eslint.config()`; this config-only step writes the configuration and declares the
linter dependencies without trying to run ESLint. TypeScript is needed for the default TypeScript
rules; omit it when using `eslint.config({ typescript: false })`.

Then add `eslint.fix()` to the blueprint list, as in this final configuration:

```bash
pnpm pjt remodel
pnpm pjt inspect
```

The first command now formats fixable lint violations with the project-local ESLint executable.
The check exits zero when the managed configuration and lint checks are clean. Nonfixable rule
violations still need source edits; `--fix` does not guarantee that every file satisfies every rule.

`fix()` declares the `exec` permission for `eslint --fix .` and `eslint .`. Without that
permission granted, the command does not run and `pjt.exec.command-not-permitted` is reported.

## Options

```ts
eslint.config({
  ignores: ["build"], // appended to the defaults: dist, coverage, node_modules
  typescript: true, // default: true; adds typescript-eslint and its recommended rules
  prettier: "config", // default: null; adds eslint-config-prettier
  extends: "eslint.rules.mjs", // default: none; your own rules, imported last
})
eslint.fix()
```

The config file is `eslint.config.mjs`, so it loads the same way in ESM and `"type": "commonjs"`
projects. It is owned, so projitect rewrites it on every `pjt remodel`. To add your own rules, pass
`extends: "eslint.rules.mjs"`: the generated config imports that module and appends its default
export (an array of flat-config entries) last. projitect seeds the file once as `export default []`
and never overwrites it afterwards, so it is yours to edit.
`blueprint-next` also owns `scripts.lint`, so it cannot be combined with `eslint.config()`.
The blueprint targets ESLint 9, which supports every Node version projitect does.
The TypeScript rules need `typescript` installed in the project (typescript-eslint supports
versions below 6.1); the blueprint does not manage that dependency.

## Order relative to `prettier.fix()`

Exec operations run last, after all file operations, and in the order the blueprints appear in the
array. Place `eslint.fix()` before a Prettier fix command and Prettier has the final word on
formatting; place it after and ESLint does. For most projects, run ESLint first and Prettier last.

## eslint-config-prettier or eslint-plugin-prettier

- **`eslint-config-prettier`** turns off ESLint rules that conflict with Prettier. Run Prettier as
  its own step. This is what `prettier: "config"` sets up, and it is the recommended choice: lint
  stays fast, and formatting differences are never reported as lint errors.
- **`eslint-plugin-prettier`** runs Prettier as an ESLint rule, so `eslint --fix` also formats.
  Formatting differences show up as lint errors and the run is slower. If you want it, add the
  plugin to your `extends` module; `eslint.config()` does not generate it.
