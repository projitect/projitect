A blueprint is just a TypeScript module that exports functions returning `Blueprint` values.
Anyone who can write Effect can write a blueprint.

## Your first blueprint

A region-mode blueprint that adds a section to `README.md`. Reach for `markdownSection` —
the SDK helper that bakes in the HTML comment delimiters so the markers don't render in the
published file:

```ts
import { markdownSection } from "@projitect/blueprint"
import type { Blueprint } from "@projitect/core"

export const myReadmeSection = (): Blueprint.Blueprint =>
  markdownSection({
    id: "my-org:readme:intro",
    version: "1.0.0",
    description: "Intro section for org-standard README",
    path: "README.md",
    content: "This project is part of My Org. See https://my-org/handbook.\n",
  })
```

Project maintainers consume it via:

```ts
import { pjt } from "@projitect/cli"
import { myReadmeSection } from "@my-org/readme-blueprints"

export default pjt({ blueprints: [myReadmeSection()] })
```

That's the whole API for static content blueprints.

## Section helpers

Two thin wrappers over `regionFile` are exported for the two most common region shapes —
they exist because the names document intent and the right comment delimiters are baked in:

- **`markdownSection`** for HTML/MDX/XML files. Fences with `<!-- pjt:<id> start -->` and
  `<!-- pjt:<id> end -->`. The markers render invisible in markdown output, so READMEs stay
  clean for human readers. Use for `README.md`, `AGENTS.md`, `CONTRIBUTING.md`, MDX docs,
  any HTML/XML file.
- **`ignoreSection`** for `#`-comment ignore-style files. Fences with `# pjt:<id> start`
  and `# pjt:<id> end`. Use for `.gitignore`, `.eslintignore`, `.prettierignore`,
  `.dockerignore`, `.npmignore`.

```ts
import { ignoreSection, markdownSection } from "@projitect/blueprint"

ignoreSection({
  id: "my-org:eslintignore:generated",
  version: "1.0.0",
  path: ".eslintignore",
  content: "dist/\nbuild/\ncoverage/\n",
})

markdownSection({
  id: "my-org:agents:rules",
  version: "1.0.0",
  path: "AGENTS.md",
  content: "Always run `pnpm check-all` before merging.\n",
})
```

For other comment styles (`//`, `--`, `;`), drop down to `regionFile` directly and pass the
prefix you need.

## Markdown snippet packages

A package of reusable `AGENTS.md` / `README.md` snippets is a set of `markdownSection`
blueprints. `@projitect/blueprint-markdown` is the reference; its shape:

```ts
import { markdownSection } from "@projitect/blueprint"
import type { Blueprint } from "@projitect/core"

export interface SnippetOptions {
  readonly version?: string
  readonly content?: string
}

export const agentsVerification = (options: SnippetOptions = {}): Blueprint.Blueprint =>
  markdownSection({
    id: "my-org:agents:verification",
    version: options.version ?? "1.0.0",
    path: "AGENTS.md",
    content: options.content ?? "## Verification\n\nRun the full check before claiming done.\n",
  })
```

- **The `id` is the owner id.** It is the key in `.pjt.lock` and the name in the region markers
  (`<!-- pjt:my-org:agents:verification start -->`). Namespace it (`<org>:<file>:<snippet>`) and
  never change it once published — a renamed id looks like a removed snippet plus a new one.
- **The `version` changes, the `id` does not.** Bump `version` whenever the content changes. After
  a package upgrade, `pjt inspect` reports the file as drifted and `pjt remodel` rewrites only the
  region that snippet owns.
- **Read `version` from your `package.json`** (a JSON import) instead of a hand-edited constant, so
  every release bump reaches `.pjt.lock` and `pjt inspect` can report `↑ upgrade <id> 1.0.0 → 1.1.0`.
  Every first-party blueprint does this. Set `rootDir` to `.` and include `package.json` in your
  `tsconfig.json`, so the build emits `dist/package.json` next to `dist/src/` and the import
  resolves from source, from `dist` and from the packed tarball alike.
- **One region per snippet.** Two blueprints with the same `id` in one file fail with
  [`pjt.plan.conflict-region`](/errors/pjt.plan.conflict-region/).
- **Expose the snippets as a blueprint set** so `pjt add <package> --section a,b` works:

  ```json
  "projitect": {
    "type": "blueprint-set",
    "import": "import { markdownSnippets } from \"@projitect/blueprint-markdown\"",
    "callTemplate": "markdownSnippets.{section}()",
    "sections": ["agentsVerification", "agentsCommits", "readmeLicense"]
  }
  ```

See the [markdown-snippets example](/examples/markdown-snippets/) for consuming them.

## Computed blueprints (using Effect)

When you need to read state, branch on detected configuration, or compose multiple operations,
write the `plan` Effect yourself:

```ts
import { BlueprintFileSystem, type Blueprint, type ChangeSet } from "@projitect/core"
import { computed, readPackageJson } from "@projitect/blueprint"
import { Effect } from "effect"

export const reactConfig = (opts: { typescript: boolean }): Blueprint.Blueprint =>
  computed({
    id: "my-org:react:config",
    version: "1.0.0",
    permissions: [
      { kind: "read", glob: "package.json" },
      { kind: "write", glob: "src/index.tsx" },
      { kind: "write", glob: "src/index.jsx" },
    ],
    plan: Effect.gen(function* () {
      const fs = yield* BlueprintFileSystem
      const pkg = yield* readPackageJson()
      // ... compute the change set based on package state ...
      return { operations: [] } satisfies ChangeSet.ChangeSet
    }),
  })
```

You get the full Effect surface area: `Effect.if`, `Effect.when`, `Effect.forEach`, error
handling via `Effect.catchTag`, custom Layers for shared services, and so on.

## Owning `package.json` keys

A merge-mode blueprint (`jsonMerge`) owns the dotted keys it lists in `ownedKeys`, such as
`scripts.prepare` or `devDependencies.husky`. List leaves, not a whole parent like `scripts`, and
keep `ownedKeys` identical to the keys in `value`.

| Situation                                      | Result                                                                      |
| ---------------------------------------------- | --------------------------------------------------------------------------- |
| Two blueprints list the same key               | `pjt.plan.conflict-merge` at plan time; one owner per key, no composition   |
| Different keys under the same parent           | Both apply (`scripts.changeset` and `scripts.prepare`)                      |
| Merge mixed with `owned` or `seed` on the file | `pjt.plan.conflict-owned`                                                   |
| Keys you added yourself                        | Preserved by `pjt build` and `pjt remodel`; removal deletes only owned keys |
| An owned key edited by hand                    | `pjt inspect` reports `~ modify package.json (JSON merge)`; remodel resets  |
| A key you set that a blueprint also owns       | The blueprint's value wins                                                  |

The husky blueprint is the only first-party owner of `scripts.prepare` (`husky`). The framework
blueprints own `dev`/`build`/`preview` (React) and `dev`/`build`/`start`/`lint` (Next.js), so
the two conflict on `scripts.build`; Vitest owns `test` and `test:watch`; Changesets owns
`changeset` and `version-packages`.

## Permissions

Every blueprint declares what it needs:

```ts
permissions: [
  { kind: "read", glob: "package.json" },
  { kind: "write", glob: ".gitignore" },
  { kind: "write", glob: "src/**/*.ts" },
]
```

The `BlueprintFileSystem` rejects operations outside this set with `pjt.fs.permission-denied`.
**Declare what you need and nothing more** — project maintainers read this list when deciding
whether to install your blueprint.

Globs support `*` (any non-slash chars), `**` (any chars including slashes) and `{a,b}`
alternation, so `src/**/*.{ts,tsx}` covers both extensions in one entry. Alternatives may be
empty or nested, and a path is permitted only if it matches one of them.

## Post-apply commands

`exec` declares a command that runs after every file operation has succeeded, such as a
formatter:

```ts
import { exec } from "@projitect/blueprint"

export default exec({
  id: "my-org:format",
  version: "1.0.0",
  check: "pnpm lint",
  fix: "pnpm lint:fix",
})
```

- `fix` is the command `pjt build` and `pjt remodel` run from the project root. Commands run in
  blueprint order; a command several blueprints declare runs once. Exec operations are not
  recorded in the lockfile, so the fix runs on every remodel.
- `check` is the command that reports whether the fix is needed. It is carried in the plan next to
  the fix as metadata: build and remodel never run it and it does not decide whether the fix runs.
  `pjt inspect` currently reports `pjt.inspect.operation-unsupported` for a project with exec
  operations; it does not run the check yet.
- The permission is derived for you: `{ kind: "exec", command }` entries for the fix and
  the check, matched as exact strings. A command outside the declared set fails with
  `pjt.exec.command-not-permitted`. Add further permissions with `extraPermissions`.

Two blueprints that declare exec operations never conflict, because an exec operation owns no path.

## directory() for scoped blueprints

To re-root a tree of blueprints under a subdirectory:

```ts
import { pjt, directory } from "@projitect/cli"

export default pjt({
  blueprints: [
    directory("docs", [
      // Each child blueprint's paths are now relative to docs/, and their write
      // permissions are restricted to that subtree.
      myReadmeSection(),
    ]),
  ],
})
```

This is useful for monorepos where the same blueprint should apply to multiple packages.

## Testing

`@projitect/test-kit` exposes an in-memory `BlueprintFileSystem` Layer:

```ts
import { makeInMemoryLayer, dumpFs } from "@projitect/test-kit"
import { Effect } from "effect"
import { myReadmeSection } from "./blueprint"
import { it, expect } from "vitest"

it("adds a region to an existing README", async () => {
  const layer = makeInMemoryLayer({ "README.md": "# Project\n\nExisting content.\n" })
  const blueprint = myReadmeSection()
  await Effect.runPromise(blueprint.plan.pipe(Effect.provide(layer)))
  const fs = await Effect.runPromise(dumpFs(layer))
  expect(fs["README.md"]).toMatchSnapshot()
})
```

## Publishing

A blueprint package's `package.json`:

```json
{
  "name": "@my-org/readme-blueprints",
  "version": "1.0.0",
  "type": "module",
  "exports": { ".": "./dist/src/index.js" },
  "peerDependencies": {
    "@projitect/blueprint": "^0.0.0",
    "@projitect/core": "^0.0.0",
    "effect": "4.0.0-rc.111"
  },
  "projitect": {
    "type": "blueprint",
    "import": "import { myReadmeSection } from \"@my-org/readme-blueprints\"",
    "call": "myReadmeSection()"
  }
}
```

Peer-dep `effect`, `@projitect/blueprint`, and `@projitect/core` — never bundle them. The
project maintainer's install resolves to a single shared copy.

### The `"projitect"` metadata field

Adding this field to your `package.json` lets `pjt add <your-package>` auto-splice your
blueprint into the user's `.pjt.ts`. Without it, `pjt add` still installs the package but
prints a "no metadata, edit `.pjt.ts` by hand" message.

Two shapes are supported:

**Single-blueprint** (one export, one call):

```json
"projitect": {
  "type": "blueprint",
  "import": "import { myBlueprint } from \"@my-org/my-blueprint\"",
  "call": "myBlueprint()"
}
```

**Blueprint-set** (multiple sections the user picks among, e.g. one per OS):

```json
"projitect": {
  "type": "blueprint-set",
  "import": "import { gitignores } from \"@projitect/blueprint-gitignore\"",
  "callTemplate": "gitignores.{section}()",
  "sections": ["macOs", "windows", "linux", "node", "next", "vscode", "jetbrains", "tsbuildinfo", "vite", "astro", "nuxt", "svelteKit", "angular", "vue", "storybook", "yarn", "pnpm", "vim", "sublimeText", "eclipse"]
}
```

`{section}` is substituted with each chosen section name. When the user runs
`pjt add @projitect/blueprint-gitignore --section macOs,node`, the splice inserts
`gitignores.macOs(),` and `gitignores.node(),` into the blueprints array.

If `--section` is omitted, **all** declared sections are added — useful for "starter kits"
where the user wants the whole bundle.

### The two marker conventions

`pjt add` splices into the user's `.pjt.ts` between two **convention markers**:

- `// pjt:imports start` / `// pjt:imports end` — for the import statement
- `// pjt:blueprints start` / `// pjt:blueprints end` — for the call lines

These are NOT lockfile-managed regions and NOT drift-checked. They're just splice anchors.
Don't confuse them with `// pjt:projitect:imports start/end`, which IS a managed region (owned
by the projitect blueprint) and IS drift-checked.

If a user has hand-edited `.pjt.ts` and removed the convention markers, `pjt add` fails with
[`pjt.add.markers-missing`](/errors/pjt.add.markers-missing/) and tells them how to restore them.

`@projitect/blueprint` exports the same splice and section logic `pjt add` uses, so tools that
edit `.pjt.ts` follow the same conventions:

- `spliceBlueprintFile({ content, blueprintFile, importLine, callLines })` — pure text-to-text
  splice; the caller reads and writes the file.
- `resolveSections` / `computeSplice` — turn a package's `"projitect"` metadata
  (`ProjitectPackageMetadata`) and a `SectionStrategy` (`All`, `Explicit` or `Ask`) into the
  import line and call lines. `resolveSections` returns a `SectionSelection` (`All`, `Chosen` or
  `Nothing`); on `Nothing` the host skips the write.
- `chooseSectionsInteractive` — the interactive section multi-select; Ctrl-C selects nothing, so
  `.pjt.ts` is left unchanged.

<Aside type="note" title="Lint rule">
  The `@projitect/blueprint` package ships an ESLint preset that forbids `node:fs` and
  `child_process` imports. Add it to your blueprint package's `eslint.config.js` so the soft sandbox
  boundary is enforced at lint time.
</Aside>
