---
title: Ownership modes
description: Every blueprint operation declares one of four modes — region, merge, owned, or seed.
---

projitect supports four ways a blueprint can own a piece of a file. Picking the right mode is
the most important design decision when authoring a blueprint.

## region — comment-fenced section in a shared text file

**When to use**: multiple blueprints can write to the same file (`.gitignore`, `.editorconfig`,
`README.md` sections, shell snippets).

```ts
import { regionFile } from "@projitect/blueprint"

regionFile({
  id: "pjt:gitignore:macos",
  version: "1.0.0",
  path: ".gitignore",
  commentPrefix: "#",
  content: ".DS_Store\n.AppleDouble\n.LSOverride\n",
})
```

On disk:

```text
# pjt:gitignore:macos start
.DS_Store
.AppleDouble
.LSOverride
# pjt:gitignore:macos end
```

The CLI splices regions in and out of the file independently. Hand-editing inside the markers
is detected as drift; hand-editing outside the markers is yours.

## merge — deep-merge into structured JSON

**When to use**: blueprint owns specific keys inside a JSON file (`package.json`,
`tsconfig.json`, etc.). Comment markers don't work in JSON — this mode replaces them.

```ts
import { jsonMerge } from "@projitect/blueprint"

jsonMerge({
  id: "pjt:react:bootstrap",
  version: "1.0.0",
  path: "package.json",
  ownedKeys: ["dependencies.react", "dependencies.react-dom", "scripts.dev"],
  value: {
    dependencies: { react: "^19.0.0", "react-dom": "^19.0.0" },
    scripts: { dev: "next dev" },
  },
})
```

Each blueprint declares **which dotted-path keys it owns**. Keys are compared segment by segment:
`scripts` covers `scripts.dev` but not `scripts.devtools`. List leaves such as `scripts.dev` or
`devDependencies.husky` unless the blueprint owns a whole subtree, because an owned parent blocks
every other blueprint from claiming anything under it.

Blueprints never compose a shared script value. Planning checks two things before any file or the
lockfile is written, and applying checks a third against the file on disk before its first write:

- **One owner per key.** Two blueprints claiming the same key, or one claiming a key that contains
  the other's (`scripts` and `scripts.test`), is a `pjt.plan.conflict-merge` error naming both owners
  and the key, in either declaration order. The human resolves it by removing the key from one of
  them. Different keys under the same parent coexist, and one blueprint declaring a key and its own
  descendant simply owns the ancestor.
- **Every written field is owned.** Each field in `value` must equal an owned key or sit under one.
  Objects are merged key by key, so each leaf is checked; arrays, scalars, `null` and an empty `{}`
  replace what is there, so each counts as a single field. A field no owned key covers is a
  `pjt.plan.unowned-merge-write` error naming the file and field.

- **No unowned ancestor is replaced.** A blueprint that owns only `a.b` and writes `{ a: { b: … } }`
  turns `a` into an object. When your file holds `a` as an array, a string, a number or `null`, and
  no owned key covers `a`, `pjt build` and `pjt remodel` stop with
  [`pjt.apply.merge-ancestor-not-object`](/errors/pjt.apply.merge-ancestor-not-object/) before any
  file or the lockfile is written. An absent or object `a` is fine, and so is one the blueprint owns.
  `pjt inspect` reports the file as drift.

`ownedKeys` and `value` can be computed from options, so the first two checks run at runtime against the real
values, not at authoring time. No ESLint rule enforces them, because lint cannot see computed values.

Keys you add yourself are kept: `pjt build` and `pjt remodel` merge the blueprint value into your
file and leave every other key alone. `.pjt.lock` records the fields each merge blueprint wrote, and
removing a blueprint deletes exactly those fields, not the whole owned key. A blueprint that owned
`scripts` and wrote `scripts.build` takes only `scripts.build` with it: the `scripts.custom` you added,
and any key another blueprint claims, stay. An object left empty by the deletion goes too. A field
the blueprint wrote as a string, number or array, and that you have since turned into an object with
children of your own, is left alone with its children. When a blueprint that stays turns a field it
wrote into an object, the new children are kept. A field it wrote that now sits under a value it
writes, such as the old children of an object it now writes as `{}`, is removed, and the empty
object stays.
`pjt inspect` reports `~ modify package.json (JSON merge)` when an owned key no longer matches,
and `pjt remodel` rewrites it to the blueprint value. A key you set that a blueprint also owns
takes the blueprint's value, so leave such keys to the blueprint. When a blueprint leaves and another
now claims an overlapping key, the departing blueprint's removal skips that key. A lockfile written
before version 3 records only the claimed key, so when its blueprint leaves while that key holds an
object, `pjt remodel` cannot tell the blueprint's fields from yours and stops with
[`pjt.remove.ambiguous-merge-claim`](/errors/pjt.remove.ambiguous-merge-claim/) before writing anything. A `package.json` that does not
parse is reported as unparseable JSON, and remodel rewrites it from the blueprint's keys alone.

## owned — single blueprint owns the whole file

**When to use**: generated code or config that no human should hand-edit (e.g. generated TS
types, lockfiles, route manifests).

```ts
import { ownFile } from "@projitect/blueprint"

ownFile({
  id: "pjt:route-manifest:generated",
  version: "1.0.0",
  path: "src/routes.generated.ts",
  content: GENERATED_ROUTES_TS,
})
```

If two blueprints claim the same path in this mode, the planner fails with
`pjt.plan.conflict-owned`. Hand-editing the file is detected as drift.

## seed — write once, never enforce

**When to use**: starter content the user is expected to customize (initial `README.md`,
boilerplate `.pjt.ts`, default `src/index.ts`).

```ts
import { seedFile } from "@projitect/blueprint"

seedFile({
  id: "pjt:readme:seed",
  version: "1.0.0",
  path: "README.md",
  content: "# My project\n\nReplace this with your own content.\n",
})
```

`pjt remodel` writes the file only if it's absent. Once it exists, `pjt inspect` ignores it
forever — including content drift. This is the escape hatch for "we want to bootstrap this once
but never own it."

## exec — a command after the files

Not a fifth ownership mode: an `exec` blueprint owns no file. It declares a command that runs
once every file operation has succeeded — typically a formatter or a code generator.

```ts
import { exec } from "@projitect/blueprint"

exec({
  id: "my-org:format",
  version: "1.0.0",
  check: "pnpm lint",
  fix: "pnpm lint:fix",
})
```

`pjt build` and `pjt remodel` run the `fix` command from the project root, after the file
operations, in blueprint order; a command declared by several blueprints runs once. A failing
command stops the run with `pjt.exec.command-failed`. The `check` command reports whether the fix
is needed. Build and remodel never run it; `pjt inspect` runs it and reports a failing check as
drift, exiting 1. Exec operations are not recorded in the lockfile, so the fix runs on every remodel.

The blueprint declares an `exec` permission for each of the two command lines, matched as exact
strings. A command outside that list fails with `pjt.exec.command-not-permitted` before anything
runs.

## Comparison

| Mode     | Multi-blueprint per file?   | Drift detected? | Best for                        |
| -------- | --------------------------- | --------------- | ------------------------------- |
| `region` | Yes (different `ownerId`)   | Yes             | `.gitignore`, README sections   |
| `merge`  | Yes (different `ownedKeys`) | Yes             | `package.json`, `tsconfig.json` |
| `owned`  | No                          | Yes             | Generated files                 |
| `seed`   | No                          | No (write-once) | Initial templates the user owns |

## What about binary files?

For v0, binary files are out of scope. `regionFile` and `ownFile` both assume UTF-8 text. A
future `binaryFile` mode tracking by content hash is on the [roadmap](/docs/roadmap/).
