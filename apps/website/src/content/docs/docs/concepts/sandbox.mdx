title: Sandbox
description: How projitect confines blueprint code, what that prevents, and what it does not.
---

A blueprint is npm-installed code that runs on your machine. projitect runs your `.pjt.ts` and
every blueprint's plan in a separate **worker process** started with Node's **permission model**,
and gives that process one way to reach your project: a permission-gated `BlueprintFileSystem`.

## Threat model

The sandbox **reduces accidental filesystem and process access** by blueprint code and its
dependencies. A blueprint that forgets to declare a permission, a dependency that reads `~/.ssh` to
"detect" something, or a helper that shells out without being asked, fails with an error instead of
quietly succeeding.

It is **not** a security boundary:

- It does **not** contain deliberately malicious code. Node's own documentation says the permission
  model does not protect against malicious code and can be bypassed.
- It does **not** defend against supply-chain attacks. Treat a new blueprint package like any new
  npm dependency and read its source before adding it.
- It provides **no OS-level confinement**: no Linux namespaces, Landlock, seccomp or container, and
  no macOS sandbox. Network access is not restricted on the supported Node versions (see below).

## How it works

`pjt build`, `pjt remodel` and `pjt inspect` start one worker per run:

1. The CLI transpiles `.pjt.ts` to plain JavaScript. Loaders such as `tsx` start a worker thread,
   which the sandboxed process is not allowed to do, so the worker only ever imports finished
   JavaScript. Bare imports stay external and resolve from your `node_modules` as usual.
2. The CLI computes the worker's **read allowlist**: its own code, the `.pjt.ts`, the dependency
   closure of `effect`, `@projitect/core`, `@projitect/blueprint` and every package your `.pjt.ts`
   imports, and the Node installation. Your project tree and your home directory are never on it.
   The closure follows each package's `dependencies` and `peerDependencies`, so a blueprint package
   must declare every package it imports.
3. The CLI starts the worker with the permission flag and one `--allow-fs-read` per allowlist
   entry. No write, child-process or worker-thread permission is granted, and the worker gets an
   empty environment.
4. The worker runs the config-time Effect and each blueprint's plan, and returns each blueprint's
   id, version, permissions and `ChangeSet` as plain data. The CLI reduces them into the plan.

Blueprint authors change nothing: blueprints still use `BlueprintFileSystem`, and the code they
write is the same.

## The permission-gated filesystem

Every `BlueprintFileSystem` call in the worker travels to the CLI over the worker's IPC channel,
where it is checked against the blueprint's declared **permissions**
(`{ kind: "read", glob: "..." }`, `{ kind: "write", glob: "..." }`):

- Paths resolve relative to the **project root**. Absolute paths and `..` escapes are rejected
  with `pjt.fs.permission-denied`.
- Symlinks are resolved to their real path and the glob is checked again, so a link inside the
  project that points outside it is denied.
- A blueprint that did not ask to write `package.json` cannot write it, even if it tries.
- Inside `directory("docs", [...])` blocks, child blueprints are **re-rooted** at `docs/`.

Errors cross the process boundary as the same typed errors the CLI raises, so a permission denial
reaches the blueprint's Effect unchanged and shows up in `pjt inspect --json` as before.

## What each Node version restricts

The worker uses the launch flag the Node documentation names for the running version. The
`engines.node` floor is `>=22.12.0`.

| Capability in the worker            | Node 22.12                        | Node 22.13+ and 24                |
| ----------------------------------- | --------------------------------- | --------------------------------- |
| Launch flag                         | `--experimental-permission`       | `--permission`                    |
| Read files outside the allowlist    | Denied (`ERR_ACCESS_DENIED`)      | Denied (`ERR_ACCESS_DENIED`)      |
| Write files directly with `node:fs` | Denied (`ERR_ACCESS_DENIED`)      | Denied (`ERR_ACCESS_DENIED`)      |
| Spawn processes (`child_process`)   | Denied (`ERR_ACCESS_DENIED`)      | Denied (`ERR_ACCESS_DENIED`)      |
| Start worker threads                | Denied (`ERR_ACCESS_DENIED`)      | Denied (`ERR_ACCESS_DENIED`)      |
| Load native addons                  | Denied                            | Denied                            |
| Network connections                 | **Not restricted**                | **Not restricted**                |
| Environment variables of the CLI    | Not passed to the worker          | Not passed to the worker          |
| `.pjt.ts` loading                   | Transpiled to JavaScript by `pjt` | Transpiled to JavaScript by `pjt` |

Node 22.12 through 24 document no network permission, so a blueprint or dependency in the worker
can open outbound connections on these versions. The sandbox does not claim otherwise.

Direct `node:fs` and `child_process` use inside blueprint packages is also rejected at lint time:
the `@projitect/blueprint` ESLint preset forbids both.

## When the worker fails

A worker that crashes, exits before returning a plan, or runs past its time limit is stopped and
reported as one of [`pjt.worker.crashed`](/errors/pjt.worker.crashed/),
[`pjt.worker.exited-early`](/errors/pjt.worker.exited-early/) or
[`pjt.worker.timed-out`](/errors/pjt.worker.timed-out/).

## What about exec?

A blueprint declares `{ kind: "exec", command: "..." }` in its permissions to name a command it may
run. The worker never starts processes: it has no child-process permission, so a blueprint cannot
shell out while it plans. `pjt build` and `pjt remodel` run the commands themselves, in the CLI
process, in a final phase after every file operation, and only a command that a blueprint's `exec`
permissions name exactly (the whole command string, no globs) is started. See
[`pjt remodel`](/docs/cli/remodel/#post-apply-commands) for the ordering, deduplication and failure
rules.
