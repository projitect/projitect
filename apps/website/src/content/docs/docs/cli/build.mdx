---
title: pjt build
description: Wipe the project tree and rebuild from blueprints. Destructive.
---

```bash
pjt build --force [--force-dirty] [--yes] [--json]
```

**Destructive.** Deletes every file under the project root except a small preserved set (see below), then applies the blueprint plan against the fresh tree. Intended for fresh greenfield scaffolds and one-shot migrations off another generator. **Not for day-to-day use** — that's what `pjt remodel` is for.

## Required + optional flags

| Flag            | Description                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `--force`       | **Required.** Without it, `pjt build` refuses to run. The wipe is too destructive to fire by accident.                          |
| `--force-dirty` | Allow wiping even when `git status --porcelain` shows uncommitted changes. Default is to refuse on a dirty tree.                |
| `--yes`         | Authorize deletion without a prompt. Required when stdin is not a terminal, including scripts and agents.                       |
| `--json`        | Print the result as `{ cancelled, wiped, remodel }`. On failure, print `{ "error": { ... } }` with the error's `id` and fields. |

## Post-apply commands

After the files are rebuilt, `pjt build` runs the blueprints' post-apply commands in a final phase, exactly as [`pjt remodel`](/docs/cli/remodel/#post-apply-commands) does: sequentially, deduplicated, only if every file operation succeeded, and each one must be named by its blueprint's `exec` permissions. The wipe has already happened by then, so a failing or refused command leaves the rebuilt files in place and `pjt build` exits nonzero with `pjt.exec.command-failed` or `pjt.exec.command-not-permitted`.

## What gets preserved

Everything else under the project root is deleted. These survive:

- `.git/`
- `node_modules/`
- `.pjt.ts`
- `.pjt.lock`
- `package.json`
- `pnpm-lock.yaml` / `package-lock.json` / `yarn.lock` / `bun.lockb`

Removals for blueprints that left `.pjt.ts` follow the same rule as [`pjt remodel`](/docs/cli/remodel/): a merge blueprint takes only the fields `.pjt.lock` records it wrote from the preserved `package.json`, and an ambiguous pre-version-3 claim stops the run with `pjt.remove.ambiguous-merge-claim` before anything is written.

The rationale: keep the manifest, the blueprint spec, the lockfile, the dependency store, and version control. Everything else regenerates from the plan.

## Prerequisites

| Check                                                    | Failure code                                                                                             |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Project root has `.git/`                                 | `pjt.git.not-a-repo`                                                                                     |
| `git status --porcelain` is empty                        | `pjt.apply.dirty-git` (override with `--force-dirty`)                                                    |
| `--force` flag is present                                | `pjt.apply.dirty-git` (with a clarifying message)                                                        |
| Non-interactive input has `--yes`                        | `pjt.apply.confirmation-required`                                                                        |
| Blueprint file imports and has a valid literal structure | `pjt.config.blueprint-file-not-found`, `pjt.loader.import-failed` or `pjt.loader.invalid-default-export` |

## Checked before anything is deleted

After the force/git checks, non-interactive input requires `--yes`. Otherwise the command stops promptly with `pjt.apply.confirmation-required` (exit 1), without importing the config or prompting.

The command imports `.pjt.ts` once and validates its default export, literal blueprint entries, permissions and nested directory structure before deletion. A missing file reports `pjt.config.blueprint-file-not-found` and tells you to run `pjt init`. An import failure reports `pjt.loader.import-failed`; a malformed literal configuration reports `pjt.loader.invalid-default-export`. These checks preserve existing files even with `--force --yes`.

In a terminal, confirmation follows preflight unless `--yes` was supplied. Declining preserves files; Ctrl-C cancels with exit130. Back up ignored content as well as committing tracked files: git cannot restore everything the wipe deletes.

## Not rolled back

Configuration-tree Effects and blueprint plans run after the wipe, so they see the fresh filesystem. Failures during their evaluation, plan conflicts, application and post-apply commands can occur after deletion. Build does not roll back the wipe or later partial writes. User module imports can also have their own side effects. Use `pjt remodel` for ordinary incremental updates.

## Output

```text
Wiped 4 entries:
  src
  tests
  docs
  scratch.md
Rebuilt 1 file from the plan:
  .gitignore
Ran 1 command:
  pnpm exec prettier --write .
```

Or, when the user declines the confirmation:

```text
Cancelled. No changes made.
```

## When to use this

- Fresh project: `pjt init` then optionally `pjt build --force --yes` to wipe any leftovers and run the plan from scratch.
- Migrating off another scaffolder: delete the other tool's lockfile, install projitect via `pjt init`, run `pjt build --force` to clear the old tree and let blueprints rebuild what they own.
- Recovering from heavy hand-editing: when `pjt remodel` would produce a confusing diff, wipe and rebuild.

For everything else, use `pjt remodel` — it's non-destructive and handles drift, removals, and upgrades incrementally.
